# 테스트 입력과 UI 문구 정리

사용자 지시: 자연어와 별도 목적 입력을 중복하지 않고, 사전조건을 선택 항목으로 둔다. 사용자의 최종 정정에 따라 기대 결과는 별도 Assertion 항목으로 유지한다. 검색어 같은 수행 입력은 자연어에 적는다.

기본 입력은 자연어·사전조건·Assertion이다. 기존 schema와 check ID는 유지하고 자연어 전체를 실행 objective로 저장한다. 기존 녹화/승인/재생 데이터와 기능은 보존한다. 변수·단계·경로 등의 세부 편집은 접힌 설정에 둔다.

개요의 홍보 문구, 승인 정책 반복 설명, 사이드바의 설명, 시범 화면의 내부 API·수용 기준을 제거한다. 제목은 화면 이름으로, 버튼은 동작으로 적고 실제 차단 사유와 비용·연결 상태는 필요한 위치에 짧게 표시한다.

샘플: 자연어 `G마켓에서 노트북을 검색하고 결과 목록을 열어 줘.` / 사전조건 `G마켓 앱이 설치되어 있다.` / Assertion `검색 결과 목록에 노트북 관련 상품이 표시된다.`

문구 변경만으로 검증 PASS를 만들지 않는다. 실제 assertion 평가·결과 저장과 새 README 연속 영상은 실제 실행 근거로 따로 확인한다. 사용자는 앞서 반복 확인 없이 진행하도록 요청했으므로 재승인 절차를 추가하지 않는다.

## 구현·검증

- 녹화 준비와 케이스 편집에서 중복 objective 입력을 제거하고 raw_text 전체를 objective로 저장한다. 사전조건과 Assertion은 독립 저장한다.
- 개요의 hero/승인 설명, 사이드바 설명, 시범의 내부 API 설명·중복 정책 구역을 제거했다. 시범은 대상·실행 준비 2개 구역이다. 상세 설정과 연결 시각은 접힌 구역에 둔다.
- JS 관련 검사 50개 통과. W10/W11/W21, 녹화 진입/초안, 비용 요약, 녹화 검토 UI 회귀 32개 통과. 템플릿 59개 구문 검증, git diff --check 통과.
- 실제 웹에서 새 초안 저장→케이스 편집→자연어 수정 저장→다시 열기를 확인했다. DB 대조에서 objective=raw_text, 기존 Assertion ID·값과 사전조건 보존, jobs=0을 확인했다.
- 별도 읽기 전용 리뷰에서 중요한 회귀 결함은 발견되지 않았다. 검증 캡처는 `.review-work/ui-refinement/`에 두며 영상 산출물로 취급하지 않는다.
- 실제 Assertion 실행 판정·새 README 영상 촬영을 완료한 것으로 보고하지 않는다.
